# Alpine Peak CDK

Deployed via GitHub Actions only — no local CDK commands required.

```text
AlpinePeakStack
  → ECS cluster: alpine-peak-ski-shop (CDK-managed)
  → Fargate service: alpine-peak-ski-shop
  → target group: alpine-peak-production-cdk-tg
  → task definition family: alpine-peak-ski-shop
```

Three containers in one task, routed through Nginx sidecar:
```text
front-end              :80   → React SPA
back-end-express-socket-io-api :5000 → Express/Socket.io API
back-end-dotnet-api    :5001 → .NET 9 API
```

## Resource ownership

- `SharedDomainsStack` owns the hosted zone and ACM certificate.
- `SharedInfrastructureStack` owns the shared ALB and HTTP/HTTPS listeners.
- `AlpinePeakStack` owns its root A-alias, listener rule, target group, ECS cluster, task definition, and service.
- `AlpinePeakStack` imports shared hosted-zone, ALB, and listener outputs instead of hard-coding their physical IDs.

## Drift repair

The deployment pipeline runs `cdk deploy --revert-drift`. This creates a drift-aware CloudFormation change set that compares the CDK template with the actual AWS resources and restores supported resources to the template definition.

If the Alpine Peak listener rule is manually changed or deleted, the next deployment restores it from CDK. The workflow fails instead of continuing if CloudFormation cannot reconcile the drift.

ACM validation CNAMEs are generated by ACM and are not separate resources in this stack, so this drift repair does not cover those records.

## Shared resources (referenced, not created)

CDK does NOT create or manage:
- ALB (`consolidated-load-balancer`) and other sites' listener rules
- VPC, subnets, security groups, route tables
- RDS PostgreSQL instance
- MongoDB Atlas connection
- Secrets Manager keys (JWT, OAuth, database credentials)

These identifiers are kept in `alpine_peak_existing_resources.py`.
